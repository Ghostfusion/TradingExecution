# LLM/Agent Safety and Operational Design Inside a Trading Loop

**Bottom line**

1. The defensible architecture is: the LLM classifies, ranks, cites, and argues — the deterministic gate computes every number that touches money, and it is the only component with order-submission authority.
2. This is not a taste preference: SEC 17 CFR 240.15c3-5(c)(1)(ii) already requires pre-trade rejection of orders that exceed price/size parameters "or that indicate duplicative orders" — the exact control whose absence cost Knight Capital $440M in ~45 minutes [25][53].
3. The LLM reliability literature closes the loop: constrained decoding gets schema adherence to 100% where prompting got <40% [14], but format restriction itself degrades reasoning [13] and a single irrelevant clause drops accuracy up to 65% [16], so numbers must be computed out of band.
4. Operationally the binding constraints are boring and checkable: 50 ms clock tolerance [26], a heartbeat with a grace window [47], query-before-retry idempotency [28][29][32], and an append-only hash-chained ledger [33].

Labels used below: **PROVEN** (primary source states it), **REPORTED** (secondary/vendor claim, sample and assumptions named), **CONTESTED** (literature disagrees), **INFERENCE** (my derivation, marked as such).

## Findings

### A. LLM-as-filter, not order-placer

1. **PROVEN** — Constrained decoding, not prompting, is what makes schema adherence reliable. OpenAI reports `gpt-4o-2024-08-06` with Structured Outputs scoring **100%** on its complex-JSON-schema eval versus **<40%** for `gpt-4-0613` with prompting alone; the mechanism is explicitly "constrain our models to only tokens that would be valid according to the supplied schema" [14]. **PROVEN** — The current docs state the guarantee as "the model will always generate responses that adhere to your supplied JSON Schema" [15].
2. **PROVEN** — The guarantee has exactly two escape hatches, both programmatically detectable: a safety refusal is surfaced as a distinct `refusal` string field, and premature interruption is signalled by `finish_reason` [14]. INTERENCE: a validator that does not branch on both is not actually enforcing the schema.
3. **PROVEN** — Format restriction is not free. "Let Me Speak Freely?" finds "a significant decline in LLMs' reasoning abilities under format restrictions" and that "stricter format constraints generally lead to greater performance degradation in reasoning tasks" [13]. Design consequence: keep the *reasoning* free-form and out-of-band; constrain only the small decision record.
4. **PROVEN** — LLM arithmetic is not a number sense. GSM-Symbolic shows performance declines across all models "when only the numerical values in the question are altered", and that adding a single clause that looks relevant but is not needed for the answer causes "significant performance drops (up to 65%) across all state-of-the-art models" [16]. **INFERENCE:** an LLM that computes a position size from a text template is computing against a distribution it has not seen.
5. **PROVEN** — Multi-step tool use is unreliable at production grade. τ-bench: "even state-of-the-art function calling agents (like gpt-4o) succeed on <50% of the tasks, and are quite inconsistent (**pass^8 <25%** in retail)" [17]. A single-shot classify-and-return is a different risk class from a multi-turn tool-using agent; only the former belongs near a trading loop.
6. **PROVEN** — Structured-output tooling exists, but the *semantics* of the bounded field are ours to define. OWASP LLM05 states the control plainly: "Treat the model as any other user, adopting a zero-trust approach, and apply proper input validation on responses coming from the model to backend functions" [3].
7. **PROVEN** — Excessive Agency's root causes are enumerated as "excessive functionality; excessive permissions; excessive autonomy", and the mitigations include minimize extensions, avoid open-ended extensions (no "run a shell command / fetch a URL"), minimize extension permissions, execute in the user's context, require human approval for high-impact actions, and **complete mediation** — "Implement authorization in downstream systems rather than relying on an LLM to decide if an action is allowed" plus log/monitor and rate-limit [4]. That is the canonical statement of "LLM proposes, deterministic gate disposes".
8. **PROVEN** — Validation must be at the boundary the model does not control. LLM05's example attack scenario #2 is precisely a summarizer that reads an injected instruction from a page and exfiltrates via unvalidated output [3].
9. **PROVEN** — Token/cost exhaustion is a first-class risk: LLM10 (Unbounded Consumption) names "denial of wallet", model extraction and side channels, and prescribes input validation, quotas, rate limiting, timeouts/throttling, sandboxing, bounded queued actions and logging/anomaly detection [5]. INFERENCE: an unbounded agent token budget is a denial-of-wallet exposure on your own API key.

### B. Finance-specific LLM evaluations and their honest limits

10. **PROVEN** — TradingAgents is self-described as a research scaffold. Its README states: "TradingAgents framework is designed for research purposes… not intended as financial, investment, or trading advice", "two runs of the same ticker and date can differ. This is expected… not a defect", and — decisively for anyone quoting its returns — "**Backtest results are not guaranteed to match any published figure.** Returns depend on the model, the temperature, the date range, data quality…" [20]. The paper's abstract claims "notable improvements in cumulative returns, Sharpe ratio, and maximum drawdown" without stating a cost model [19].
11. **PROVEN, load-bearing** — The same repository has since shipped *look-ahead and point-in-time fixes*: v0.3.1 (2026-07) lists "Alpha Vantage look-ahead filtering"; v0.4.0 (2026-08) lists "look-ahead / point-in-time fixes across FRED macro, social sentiment, and the decision-log memory" [20]. **INFERENCE:** any figure quoted from pre-2026 TradingAgents runs was produced by a build the maintainers now treat as look-ahead-contaminated.
12. **REPORTED** — Widely circulated TradingAgents headline numbers (e.g. AAPL +26.62% cumulative, Sharpe 8.21 over 2024-01-01→2024-03-29) come from secondary summaries, not the paper's abstract, and are explicitly disclaimed by the authors' own README [20]. Treat as a lead, not evidence.
13. **PROVEN** — FinMem contributes an architecture (Profiling / layered Memory / Decision-making) and reports leading performance against algorithmic agents on a scalable real-world dataset; the abstract contains **no** slippage, commission, impact or capacity model [21].
14. **PROVEN** — Alpha-GPT frames LLM use as human-AI *interactive alpha mining* (a research-assistant role), and demonstrates alpha-mining experiments, not live trading [22].
15. **PROVEN** — The best-known headline is about a non-tradable measurement. Lopez-Lira & Tang: GPT-4 captures initial market responses with "approximately **90% portfolio-day hit rates for the non-tradable initial reaction**"; the *predictable* part is the subsequent drift, "especially for small stocks and negative news"; and "strategy returns decline as LLM adoption rises" [23].
16. **PROVEN** — LLM backtests are contaminated by construction. Glasserman & Lin study look-ahead bias in GPT sentiment backtests and identify two effects: look-ahead bias (training/test overlap) and a **distraction effect** from company-specific priors; within the training window, *anonymized* headlines can outperform, i.e. the priors hurt [24] (search-derived; primary not fetched in this session). **REPORTED/INTERENCE:** the practical rule is point-in-time inputs plus anonymized/held-out evaluation.
17. **CONTESTED** — Broad finance-LLM surveys report strong performance on classification-style finance NLP (sentiment, headline categorisation) and sharp weakness on financial QA, multi-step reasoning, **numerical accuracy** and summarisation, with hallucination treated as a benchmarkable failure mode (FinBen, FinanceBench/FinanceQA, XFinBench, AveniBench, BizFinBench, PHANTOM, FAITH) [search-derived]. The "it works" and "it doesn't" camps are measuring different tasks; the split is exactly classification (usable) vs generation-of-numbers (not).
18. **PROVEN** — Standardised adversarial evaluation exists and should be used instead of ad-hoc prompt lists: HarmBench compares 18 red-teaming methods against 33 target LLMs and defenses [18].

### C. Guardrail frameworks and the "proposes/disposes" mapping

19. **PROVEN** — OWASP Top 10 for LLM Applications 2025 enumerates LLM01 Prompt Injection, LLM02 Sensitive Information Disclosure, LLM03 Supply Chain, LLM04 Data and Model Poisoning, **LLM05 Improper Output Handling**, **LLM06 Excessive Agency**, LLM07 System Prompt Leakage, LLM08 Vector and Embedding Weaknesses, LLM09 Misinformation, **LLM10 Unbounded Consumption** [1].
20. **PROVEN** — OWASP is explicit that prompt injection is not solved: "Given the stochastic influence at the heart of the way models work, **it is unclear if there are fool-proof methods of prevention** for prompt injection." The listed mitigations are behavioural, not proofs: constrain model behaviour; "Define and validate expected output formats… and **use deterministic code to validate adherence** to these formats"; input/output filtering; privilege control and least privilege; human approval for high-risk actions; segregate and identify external content; conduct adversarial testing and attack simulations [2].
21. **PROVEN** — NIST AI 600-1 (Generative AI Profile, July 2024) is the cross-sector companion to the AI RMF, structured by the four AI RMF functions **Govern / Map / Measure / Manage**, and defines 12 GAI risks including **Confabulation**, **Information Security**, **Human-AI Configuration** and **Value Chain and Component Integration** [7]. Directly quotable control actions from its Section 3 action tables:

    - **MP-5.1-005**: "Conduct adversarial role-playing exercises, GAI red-teaming, or chaos testing to identify anomalous or unforeseen failure modes."
    - **MS-2.3-002**: "Evaluate claims of model capabilities using empirically validated methods."
    - **MS-2.5-001**: "Avoid extrapolating GAI system performance or capabilities from narrow, non-systematic, and anecdotal assessments."
    - **MS-2.5-003**: "Review and verify sources and citations in GAI system outputs during pre-deployment risk measurement and ongoing monitoring activities."
    - **MS-2.6-005**: "Verify that GAI system architecture can monitor outputs and performance, and handle, recover from, and repair errors when security anomalies, threats and impacts are detected."
    - **MS-2.7-007**: "Perform AI red-teaming to assess resilience against… GAI attacks (e.g., prompt injection), ML attacks (e.g., adversarial examples/prompts, data poisoning, membership inference, model extraction, sponge examples)."
    - **MS-1.1-009**: track risks that *cannot* be measured and carry them as residual. [7]

Defense-in-depth is therefore mandatory, not optional.
23. **PROVEN** — MITRE ATLAS is the ATT&CK-style knowledge base for AI systems; the relevant identifiers, cross-referenced from OWASP's own LLM01 page, are **AML.T0051 LLM Prompt Injection**, **AML.T0051.000 (Direct)**, **AML.T0051.001 (Indirect)**, **AML.T0054 LLM Jailbreak**, with **AML.T0053 AI Agent Tool Invocation** for tool abuse [2][9]. 2025 addition themes include RAG poisoning, prompt obfuscation, model malware embedding, and agent-side context poisoning, thread injection, credential harvesting and exfiltration via tool invocation [9].
24. **PROVEN** — OWASP has published an agentic counterpart: the **OWASP Top 10 for Agentic Applications 2026**, ASI01–ASI10, led by **ASI01 Agent Goal Hijack** and **ASI02 Tool Misuse & Exploitation**, then Identity & Privilege Abuse, Agentic Supply Chain, Unexpected Code Execution, Memory & Context Poisoning, Insecure Inter-Agent Communication, Cascading Failures, Human-Agent Trust Exploitation, Rogue Agents [6].
25. **PROVEN** — EU AI Act timing (as of the 2026-08-31 timeline update): obligations were scheduled to apply 2 Aug 2026; Annex III stand-alone high-risk systems were deferred to **2 Dec 2027** and high-risk AI embedded in regulated products to **2 Aug 2028**; **Article 50 transparency** duties applied from **2 Aug 2026**, with a marking grace period to 2 Dec 2026 [10]. **INFERENCE:** Annex III financial high-risk items are creditworthiness/credit scoring and certain insurance [10], so a personal, non-advisory day-trading assistant is unlikely to be "high-risk" by classification — but a *deployer* of the research layer toward third parties would change that answer, and Article 50 duties (disclosure that a human is interacting with an AI system) are live now.

HarmBench is the standardised *scoring* layer [18].

### D. Prompt injection via market data (finance-specific)

27. **PROVEN** — The canonical model is Greshake et al.: an LLM-integrated application is compromised by instructions hidden in content it *retrieves*, not instructions the user types. This is the 2023 paper that established indirect prompt injection as the practical threat for anything that reads documents [11].
28. **PROVEN, real incident** — **EchoLeak (CVE-2025-32711)**: a zero-click indirect prompt injection in Microsoft 365 Copilot enabling "remote, unauthenticated data exfiltration via a single crafted email", achieved by chaining a bypass of Microsoft's XPIA classifier, circumventing link redaction with **reference-style Markdown**, exploiting **auto-fetched images**, and abusing a Teams proxy permitted by the CSP — "without user interaction". The authors' recommended mitigations are prompt partitioning, enhanced input/output filtering, **provenance-based access control**, and strict CSPs [12]. **INFERENCE (direct analogue):** a news headline, an 8-K, or a sell-side note is attacker-controlled text; any auto-fetched image or Markdown link in an LLM-facing UI is an exfiltration channel, and the fix is provenance (only cite what the fetch layer observed) plus rendering hygiene.
29. **PROVEN** — OWASP LLM01's example scenarios map 1:1 onto a market-data feed: **Scenario #4** (poisoned RAG document alters model output), **Scenario #5** (CVE-2024-5184 prompt injection in an LLM email assistant), **Scenario #6 payload splitting** (malicious prompt fragments in a résumé that combine inside the model), **Scenario #7 multimodal injection** (instruction hidden in an image alongside benign text), **Scenario #8 adversarial suffix**, **Scenario #9 multilingual/Base64/emoji obfuscation** [2].
30. **PROVEN** — MCP is an active attack surface, not a convenience layer. **Tool poisoning** (Invariant Labs, Apr 2025): malicious instructions hidden in a tool's **description** field — read by the model as trusted context, invisible to the user — steering the agent into unauthorised actions and exfiltration [55] (search-derived). **CVE-2025-49596**: critical RCE in Anthropic's MCP Inspector **< 0.14.1**, via an unauthenticated proxy with no network/origin restrictions, triggered by a crafted request from a web page or an attacker on the same network, achieving code execution on the developer host [56] (search-derived). OWASP now publishes "A Practical Guide for Secure MCP Server Development" [59].
31. **PROVEN** — Disinformation reaches prices: NIST records that a synthetic image of a Pentagon blast "went viral and briefly caused a drop in the stock market" as an example of GAI-enabled information-integrity risk [7]. A system that trades on headlines has a disinformation exposure, not just a prompt-injection exposure.
32. **INFERENCE from [2][4][12][30]** — the finance-specific control set is: (a) market text is untrusted data, never instructions; (b) the retrieval layer, not the prompt, decides provenance, and the decision record must carry a provenance id the LLM cannot mint; (c) the LLM never receives the ability to fetch URLs, read files, or call the broker; (d) the MCP tool descriptions we expose are themselves an injection surface and must be hash-pinned and reviewed on change (rug-pull defence, Cf. ASI04/ASI06 [6]).

### E. Ops for a supervised trading daemon (2026)

33. **PROVEN** — Clock synchronization is a written rule, not best practice. FINRA Rule 4590 requires members to synchronize business clocks to a FINRA-designated time source; **computer** clocks recording the date/time of NMS-securities, standardized-options and OTC-equity events must be within **50 milliseconds of the NIST atomic clock**, with the tolerance spanning the provider-vs-NIST difference, transmission delay and clock drift; other clocks remain at **1 second** [26]. FINRA Regulatory Notice 16-23 set the 50 ms standard effective 2016-08-15, with compliance by 2017-02-20 (millisecond-capable systems) and 2018-02-19 (the rest) [27].
34. **REPORTED** — CAT clock standards are 50 ms for Industry Members' business clocks, with some Participant standards at **100 microseconds** [27] (search-derived). A retail single-account operator is not a CAT reporter, but the 50 ms figure is the right engineering target (INFERENCE).
35. **REPORTED** — NTP accuracy bands: public internet ~**10–50 ms**; well-run LAN **better than 1 ms** (down to ~200 µs); PPS/GPS **microseconds**. chrony's own error bound is `clock_error ≤ |system_time_offset| + root_dispersion + 0.5·root_delay`. Leap-second modes are `system`, `step`, `slew`, `ignore`; at default `maxslewrate` a Linux slew takes about **12 seconds** [chrony docs, search-derived]. Chosen policy must be written down because `step` produces a 1-second discontinuity in timestamped market records.
36. **PROVEN** — Windows can hit the target if configured: Microsoft states "You can achieve down to **one-millisecond** time accuracy in your domain"; W32Time uses NTP over **UDP 123**; `w32tm /stripchart` samples the offset; W32Time recommends **three or more** time servers (and if only two, deprioritise one with the `NtpServer` `UseAsFallbackOnly` flag `0x2`); `MaxAllowedPhaseOffset` decides whether a clock is slewed or stepped [44]. **INFERENCE:** a single-workstation Windows deployment therefore needs an explicit external NTP peer list, not the domain default, plus an offset alarm.
37. **PROVEN** — Linux process supervision: systemd.service supports `Type=notify` with `sd_notify` "READY=1" (so "started" means the app said so, not that a fork returned), `Type=dbus`, `notify-reload` with `RELOADING=1`/`READY=1` and `MONOTONIC_USEC`, and the docs explicitly recommend `exec`/`notify` over `forking` and note PID files "should be avoided in modern projects" [41].
38. **PROVEN** — The Windows equivalent of "make `py -3.12` a supervised service" is NSSM: it installs an arbitrary exe/script as a Windows service, with `AppExit Default Restart`, `AppThrottle` restart throttling, `AppRestartDelay` mandatory delay between restarts, `AppStdout`/`AppStderr` redirection with size/age-based rotation, and `ObjectName` service-account control [42]. Task Scheduler is the boot/event trigger layer (triggers: at a time, on boot, on logon, on event, on idle) but has no supervision semantics [43].
39. **PROVEN** — Container restart policies are `no` / `on-failure[:max-retries]` / `always` / `unless-stopped`, and a policy "only takes effect after a container starts successfully… up and for at least **10 seconds**", which is the anti-restart-loop guard; Docker explicitly warns "Don't combine Docker restart policies with host-level process managers" [45]. Kubernetes expresses liveness separately (probe failure → kill and restart; success is ≥200 and <400; `initialDelaySeconds` + `periodSeconds`) [46].
40. **PROVEN** — Heartbeats/dead-man's switch semantics worth copying: Healthchecks.io defines states New / Up / **Late** / **Down** / Paused, where the check goes *late* at the scheduled moment and *down* — firing alerts — only after the configured **Grace Time** elapses; ping URLs accept `/start`, `/fail`, `/<exitcode>`; and start-without-success beyond grace is treated as failure. It also instructs treating ping UUIDs and project keys as secrets [47].
41. **PROVEN** — Alerting discipline with numbers: Google SRE's four golden signals are latency, traffic, errors and saturation; "I can only react with a sense of urgency a few times a day before I become fatigued"; every page must be actionable and require intelligence; prefer symptoms for paging and causes for debugging; "email alerts are of very limited value"; and page frequency is reviewed as incidents per shift, quarterly, with management [39].
42. **PROVEN** — Structured telemetry: OpenTelemetry's signals are traces, metrics, logs and baggage; the log data model requires distinguishing `Timestamp` (when the event happened at the source) from `ObservedTimestamp` (when the collector saw it) and normalises severity to `SeverityNumber` (1–4 TRACE … 21–24 FATAL, ≥17 = error) with W3C `TraceId`/`SpanId` correlation [40]. **INFERENCE:** for a trading daemon the Timestamp/ObservedTimestamp split is exactly the stale-data detector: a large gap is a stalled feed, not a slow disk.
43. **PROVEN** — Market calendars are code, not a service. pandas_market_calendars ships calendars as package code and "does not request market hours from a server at runtime. To receive corrected or updated market hours, install a newer package release or update the source code", and mirrors exchange_calendars' version rather than a live feed; it carries 50+ calendars and moved to `zoneinfo` in v5.0 [49]. exchange_calendars exposes tz-aware UTC session boundaries and the primitives a scheduler needs: `is_session`, `sessions_in_range`, `session_minutes`, `previous_close`, `trading_index`, with NYSE early closes visible directly in the schedule (2012-07-03 close 17:00 UTC vs 20:00 normally) [50].
44. **INFERENCE from [49][50]** — the DST failure mode is not "DST is unhandled"; it is that the *pinned* calendar version is part of the deployment and must be in the lockfile, and that all internal timestamps are UTC while only display and exchange-session boundaries are America/New_York. A calendar-version change is a release that requires a full replay.
45. **REPORTED** — Backup/DR baseline: CISA's **3-2-1** rule (3 copies, 2 media types, 1 off-site), with **RTO** = maximum acceptable downtime and **RPO** = maximum acceptable data loss, backup frequency set by RPO and restore architecture by RTO [60] (search-derived).

### F. Testing practice for money-moving code

46. **PROVEN** — Property-based testing is the right shape for gates: Hypothesis has you "write tests which should pass for all inputs in whatever range you describe, and let Hypothesis randomly choose which of those inputs to check — including edge cases you might not have thought about", with the canonical example asserting *invariants* (same multiset, sorted order) rather than example outputs [37]. Gate invariants that matter are monotonicity, idempotence, and "more risk ⇒ never a larger size".
47. **PROVEN** — Mutation testing earns its cost when targeted. The Google ICSE-SEIP study "State of Mutation Testing at Google" found mutants are coupled with real faults and that developer exposure to mutants induces them to write more tests [38]. **REPORTED** (search-derived, primary not fetched): a 2024 Google industrial follow-up reports mutation testing integrated into code review across **24,000+ developers** and **1,000+ projects** and "does not add a significant overhead"; a 2024 open-source practice study names performance as the main objection; PIT's real-bug detection rates in 2024 comparisons were reported around **40–49%**, below LLM-based mutant generators on the same benchmarks.
48. **PROVEN** — Chaos engineering has a written method: define measurable steady state, hypothesise it will hold in control and experiment, inject real-world variables (server death, malformed responses, traffic spikes), then try to disprove the hypothesis; run in production where possible, automate continuously, and minimise blast radius [48]. For a trading daemon the "steady state" is *positions and ledger consistent*, and the injected variables are broker outage, partial fill, duplicate submission and stale data.
49. **PROVEN, the cautionary baseline** — Knight Capital, 2012-08-01: a deployment left one of eight order-routing servers on dormant "Power Peg" code; it sent erroneous child orders for about **45 minutes**, producing a **$440 million** pre-tax loss. The SEC found a violation of Rule 15c3-5 because Knight lacked (i) controls to prevent erroneous orders at the point immediately before market submission and (ii) an effective automated halt; the deployment also lacked a second-person verification step [53] (search-derived; primary order not fetched). **INFERENCE:** three of our requirements — two-person/automated deploy verification, deterministic pre-trade checks, and a kill switch — are each a documented cause of that loss.
50. **PROVEN** — The regulatory shape of the pre-trade gate is written down: 17 CFR 240.15c3-5(c)(1)(i) requires controls "reasonably designed to prevent the entry of orders that exceed appropriate pre-set credit or capital thresholds"; **(c)(1)(ii)** requires controls "reasonably designed to prevent the entry of erroneous orders, by rejecting orders that exceed appropriate price or size parameters, on an order-by-order basis or over a short period of time, **or that indicate duplicative orders**"; (c)(2) adds pre-order regulatory compliance, restricted-security checks, pre-approved account access, and "(iv) Assure that appropriate surveillance personnel receive **immediate post-trade execution reports** that result from market access"; (d) requires the controls be "under the direct and exclusive control of the broker or dealer"; and (e) requires at-least-annual review of effectiveness with CEO certification of the controls [25]. **INFERENCE:** this is the single best external specification for our gate — capital thresholds, fat-finger price/size rejection, duplicate-order rejection, immediate post-trade reporting, and an annual (we should use quarterly) effectiveness review.
51. **REPORTED** — Availability failures have prices: FINRA's 2021-06-30 settlement with Robinhood totalled about **$70 million** (**$57 million** fine plus roughly **$12.6 million** restitution), described as its largest-ever penalty, citing the 2020-03-02/03 outages during high volatility; the separate SEC December 2020 action was **$65 million** for misleading customers about payment for order flow and best execution [54] (search-derived).
52. **PROVEN** — Paper trading cannot validate execution. Alpaca states paper trading "does **not** account for: Market impact of your orders; Information leakage of your orders; Price slippage due to latency; Order queue position (for non-marketable limit orders); Price improvement received; Regulatory fees; Dividends"; fills are against the NBBO; and "your order quantity is not checked against the NBBO quantities… you can submit and receive a fill for an order that is much larger than the actual available liquidity", with partial fills occurring for a random size **10%** of the time [30]. **INFERENCE:** paper PnL is an upper bound; the cost model must come from the live-vs-model divergence monitor (§G), not from paper.
53. **PROVEN** — Rate limits are discoverable and must be obeyed: every Alpaca Broker API response carries `X-RateLimit-Limit` / `X-RateLimit-Remaining` / `X-RateLimit-Reset`; exceeding returns **HTTP 429** and the docs prescribe exponential backoff **with jitter** "ideally… not before the time indicated by `X-RateLimit-Reset`"; and — directly relevant to a hermetic test strategy — sandbox limits are far lower than production, "**Do not use the sandbox for load testing**", sandbox latency is not faithful (order routing is simulated), and the recommended approach is that "calls to Alpaca can be **stubbed or mocked**, and enable that mode for load tests" with simulated latency sampled from production [31].

### G. Reconciliation, ledger integrity, exactly-once submission

54. **PROVEN** — Idempotency has a named primitive at the broker. Alpaca's Trading API gives every order a client-supplied unique `client_order_id` (max length **128**), auto-generates one if absent, rejects a duplicate with **HTTP 422 "client_order_id must be unique"**, and exposes `GET /orders:by_client_order_id` to retrieve it — the documented retry-safety pattern [28][29]. **INFERENCE:** the correct exactly-once sequence is *derive the id deterministically* (sleeve, symbol, session, signal id) → submit → on timeout/failure **query by that id before retrying**, never mint a fresh id on retry.
55. **PROVEN** — The broker tells you its own recovery path: "Updates on open orders at Alpaca will also be sent over the streaming interface, which is the **recommended method of maintaining order state**", supplemented by querying by client-provided or system-assigned id [28][29]. A reconciliation loop that only polls is doing it the discouraged way; the streaming order-update stream plus a periodic full snapshot is the correct pair.
56. **PROVEN, generalised** — Stripe's idempotency contract shows what to replicate locally: an idempotency key up to **255 characters** (V4 UUIDs suggested); the *result* — status code and body — is saved "regardless of whether it succeeds or fails" and replayed for repeats **including 500 errors**; keys are pruned after at least **24 hours** and reuse after pruning creates a *new* request; and "The idempotency layer compares incoming parameters to those of the original request and errors if they're not the same" [32]. **INFERENCE:** a 24-hour key horizon with parameter-mismatch errors is the correct local design; a key that lives only in memory is a duplicate order after a crash.
57. **PROVEN** — Tamper-evidence has a well-specified construction. RFC 6962 (Certificate Transparency) defines an append-only log as a binary **Merkle Hash Tree** over SHA-256, with **domain-separated** leaf and node hashing (`0x00` for leaves, `0x01` for interior nodes, "required to give second preimage resistance"), **Merkle audit paths** proving a leaf's inclusion, **Merkle consistency proofs** proving that a later tree is a superset of an earlier one, and signed tree heads — precisely so that "if a log attempts to show different things to different people, this can be efficiently detected by comparing tree roots and consistency proofs" [33]. **INFERENCE:** a hash-chained ledger gives append-only + tamper-*evidence* but not tamper-*resistance*; the recoverable-value add-ons are (i) periodically publishing the head hash out-of-band and (ii) keeping consistency proofs so truncation is detectable, not just mutation.
58. **INFERENCE from [25][28][29][32][33]** — each control maps to one named failure mode: `client_order_id` + query-before-retry protects against **duplicate submission**; the streaming order-update stream + snapshot diff protects against **silent divergence after a crash**; Merkle chain + off-box head hash protects against **retroactive ledger edits** (including by the operator, which for a single-operator system is the realistic threat); the 422/403 rejection codes protect against **the gate being bypassed**; and 15c3-5(c)(2)(iv) post-trade reporting protects against **a position you did not know you had**.

### H. Observability of strategy health in production

59. **PROVEN** — Backtest claims need a multiplicity correction, and the arithmetic is simple enough to put in the report: minimum backtest length grows with the number of trials as `MinBTL ≈ 2·ln(N)/(SR*)²` years, giving roughly **1.4 y for 5 trials, 2.5 y for 10, 6.4 y for 100, 10.6 y for 1,000 and 23.7 y for 1,000,000 trials** at a target Sharpe of 1; the Deflated Sharpe Ratio additionally corrects for non-normality and for selection bias [34] (search-derived formula/table). **INFERENCE, load-bearing for our comparison window:** 2026-01-02 → 2026-09-11 is ~**8.6 months / ~173 sessions**, which is *below* MinBTL for even 5 trials at Sharpe 1. The sleeve comparison therefore **cannot** establish risk-adjusted superiority; it must be pre-registered, report bootstrap intervals, and be read as a process check.
60. **PROVEN** — Slippage attribution has a canonical decomposition: Perold's implementation shortfall (1988) is the gap between a paper portfolio and the actual portfolio, comprising the decision/arrival benchmark, execution slippage/market impact on filled shares, delay cost, **opportunity cost of unfilled shares**, and explicit fees [35] (search-derived citation). **INFERENCE:** reporting one blended "slippage" number makes signal decay and execution drift indistinguishable; report the four legs separately, per sleeve.
61. **REPORTED/INFERENCE** — Signal decay is conventionally modelled as exponential erosion `α(t)=α₀e^(−λt)` with half-life `ln2/λ`, estimated from out-of-sample/rolling metrics (information coefficient, rolling Sharpe, profit factor, hit rate) and re-estimated as regimes change; apparent alpha loss must be decomposed into signal decay vs execution drift vs capacity, and automatic de-risk/retirement triggers should fire on metric decay rather than waiting for outright loss [search-derived].
62. **PROVEN** — Capacity has a modelling framework: Almgren–Chriss (2000) is the mean-variance optimal-execution model with temporary and permanent impact, and is the standard building block for trading-capacity analysis; the empirically observed metaorder square-root law (`impact ≈ sqrt(Q/V)`) is a *separate* regularity, not part of the original AC model [36] (search-derived). **INFERENCE:** for a retail day-trading sleeve, participation `Q/ADV` is the operative capacity proxy, and the alarm should fire on participation, not on dollars.
63. **PROVEN** — The broker's own rejections are the cheapest strategy-health telemetry available, and they are typed: duplicate `client_order_id` → **422 / "client_order_id must be unique"** [28]; sub-penny price → **422 / code 42210000** ("sub-penny increment does not fulfill minimum pricing criteria") [28]; extended-hours misuse (non-limit or TIF other than day/gtc) → rejected [28]; and potential wash trade → **403 / code 40310000 "potential wash trade detected. use complex orders"**, raised when an opposite-side open order exists on the same symbol [51] (search-derived; behaviour documented, exact code string from community threads).
64. **INFERENCE, high severity for our two-sleeve design** — the wash-trade rule means **two sleeves sharing one Alpaca account can collide on the same symbol in opposite directions and have one leg rejected** (or, worse, one sleeve closing what the other just opened). This is not a risk-limit problem; it is a same-account broker constraint. The house gate must therefore own symbol-level netting/crossing policy across sleeves *before* submission, and any wash-trade rejection must be a page-level alert, never a retry.
65. **REPORTED** — Alpaca's account-level day-trading framework has changed: FINRA Rule 4210's legacy pattern-day-trader test (**4+ day trades in 5 business days** and >6% of total trades, **$25,000** minimum equity) is the historical regime; Alpaca deprecated its PDT account fields (`pattern_day_trader`, `daytrade_count`, `daytrading_buying_power`) toward removal **2026-07-06**, replacing them with an intraday-margin framework and telling developers to use `buying_power` [52] (search-derived). **INFERENCE:** the intraday sleeve must not be sized against a PDT assumption that was abolished mid-2026; it must be sized against live `buying_power` and the *current* margin rule read at runtime.

## Contested or unproven

1. **All headline LLM-trading returns are unusable as evidence.** TradingAgents' own README disclaims reproducibility ("Backtest results are not guaranteed to match any published figure") and its 2026 releases fixed look-ahead bugs across price, macro, social and memory paths [20]. FinMem and Alpha-GPT report results with no cost, slippage or capacity model [21][22].
2. **"LLMs lack numeric understanding" is contested in degree, not in direction.** Some studies report high arithmetic accuracy on selected benchmarks; the robust finding is *brittleness* — failures under magnitude changes, format changes and added clauses [16] — not total inability. The design rule survives either reading: do not let the model emit a number that matters.
3. **The distraction-vs-look-ahead decomposition is unsettled.** Glasserman & Lin find the distraction effect dominates look-ahead bias in their setting (anonymized headlines *outperform*), which contradicts the common assumption that memorisation inflates results [24]. Single study, one model family, one period.
4. **Constrained decoding vs reasoning quality is contested.** OpenAI's engineering position is that constraining to schema-valid tokens is pure win [14]; "Let Me Speak Freely?" finds significant degradation under stricter formats [13]. Both can be true (schema adherence up, reasoning down); the resolution is architectural — separate the reasoning channel from the constrained decision channel — and it is not empirically settled which tasks pay the most.
5. **Mutation testing's fault-detection value is contested.** Google reports coupling to real faults and developer benefit [38]; 2024 comparisons report PIT-class tools at ~40–49% real-bug detection, well below LLM-based generators. The PROVEN part is the *developer behaviour change*, not the detection rate.
6. **The NTP/chrony and CAT figure set (50 ms / 100 µs / 10–50 ms / 12 s slew / 200 µs LAN) comes from secondary and vendor sources**, not from fetched primary documents. FINRA Rule 4590 itself [26] and the 50 ms Notice [27] are the parts to verify in-house before writing them into a control document.
7. **The EU AI Act timetable is moving.** The 2 Dec 2027 / 2 Aug 2028 high-risk dates come from the AI Omnibus revisions recorded in a maintained timeline [10], not from reading the amended Regulation text; treat any compliance plan as provisional.
8. **Alpaca's specifics are moving under us.** PDT fields were deprecated toward removal 2026-07-06 in favour of an intraday-margin framework [52]; the wash-trade rule and rejection code come from documented behaviour plus community threads [51]; the rate-limit page fetched is the Broker API page (Trading API limits are set per partner and not published) [31]. Pin these to runtime behaviour, not to this brief.
9. **The 2026-01-02 → 2026-09-11 comparison window cannot support a Sharpe verdict.** MinBTL is ≥1.4 years even at 5 trials for Sharpe 1 [34]. Any statement of the form "sleeve A beat sleeve B on risk-adjusted return" over 8.6 months is unsupported; what is supportable is a process check with intervals and a pre-registered metric.
10. **NIST AI 600-1 and the OWASP lists are voluntary.** NIST states the guidance "remains voluntary" and "is not intended to serve as or supersede existing regulations" [8]; OWASP says explicit prevention of prompt injection may be impossible [2]. Neither is an adequate substitute for 15c3-5-style deterministic controls [25].
11. **"Silence is a signal" has a failure mode.** A dead-man's switch catches a dead process; it does not catch a live process that has stopped trading because a gate is permanently blocking (a stuck-open circuit). Pair every heartbeat with a *liveness-of-action* check (N orders attempted per session) or a blocked-gate alert.

## Implications for our system

1. **Split the decision record into two objects with different authors and different trust levels.** `LLMProposal {direction, conviction 0–100, score_adjustment_pct ∈ [−10, +10], thesis, risk_flags[], provenance_ids[]}` is model-authored and schema-enforced [14][15]. `TradeDecision {qty, limit_price, stop, tif, permission: ALLOW|BLOCK, binding_gate, opportunity_score}` is gate-authored, and the only object `orderd` will accept. The gate must reject any `TradeDecision` whose fields do not trace to gate code — this is OWASP LLM06 "complete mediation" plus 15c3-5(c)(1)(ii) in one rule [4][25].
2. **Make the two-refusal distinction a schema field, not prose.** `opportunity_score` (0–100, valuation/attractiveness) and `permission` (ALLOW|BLOCK) are independent; when `permission == BLOCK`, `binding_gate` is mandatory and must name exactly one of the house gates (CVaR, drawdown, correlation-stress, vol-regime, knife-guard, size-cap, wash/netting, data-quality). Rule: `opportunity_score` may be high while `permission` is BLOCK; a BLOCK with no named gate is a bug and must fail the run, not degrade to allow [25][7 via MS-2.5-003].
3. **Give each sleeve its own capital ledger and make the house gate the only netting authority.** 70/30 allocations live in the gate config; each sleeve carries its own daily-loss and drawdown counters (Table 2 rows 15–16). Because Alpaca rejects self-crossing orders [51], the gate must compute *symbol-level net exposure across both sleeves* before submission, and any 403/40310000 must page rather than retry [51]. This is the one place where "two sleeves, one account" is architecturally different from "two accounts".
4. **Adopt the 15c3-5 control list verbatim as the gate's specification** — (c)(1)(i) pre-set capital/credit thresholds per sleeve; (c)(1)(ii) fat-finger price/size rejection *and duplicate-order rejection*; (c)(2)(i)–(iii) pre-order compliance, restricted-security and pre-approved-account checks; (c)(2)(iv) immediate post-trade execution reports to the operator; (e) a documented review of control effectiveness with a signed certification [25]. Quarterly self-review, and keep the signed review in the repo — it is also the artifact that answers "what changed since the drill".
5. **Implement exactly-once as: deterministic id, then query, then retry.** `client_order_id = hash(sleeve|symbol|session_date|signal_id)` (≤128 chars [28]); on timeout or ambiguous failure, `GET /orders:by_client_order_id` [29] *before* any resubmission; treat 422/"client_order_id must be unique" as **success-of-a-prior-attempt**, not an error [28]. Persist the id→intent mapping on disk with a ≥24 h horizon and error on parameter mismatch, mirroring Stripe's contract [32]. Add a property test: submitting the same intent *N* times yields exactly one order [37].
6. **Replace the poll-only reconciler with stream + snapshot, and make drift a hard gate.** Subscribe to Alpaca's order-update stream as the primary order-state source (the docs' recommendation [28][29]), take a full positional snapshot at start-up, at every sleeve boundary, and hourly, and treat *any* nonzero drift or unknown position as a submission freeze [25]. Run the reconciliation drill set (§Drills) on a weekly rotation and record the measured RTO/RPO [60].
7. **Instrument the four implementation-shortfall legs separately, per sleeve.** Report decision-to-arrival, execution slippage, delay cost and opportunity cost of unfilled shares independently [35]. A blended "slippage" number cannot distinguish signal decay from execution drift, and that distinction is the whole point of the live-vs-backtest monitor.
8. **Pre-register the sleeve comparison and refuse to call a winner on 8.6 months.** Publish the metric, the period (2026-01-02 → 2026-09-11), the universe, the starting capital, the cost model and the trial count *before* looking, then report MinBTL alongside the observed Sharpe: at Sharpe 1 and 5 trials the minimum defensible backtest is 1.4 years, so this window supports "no evidence of difference" at best [34]. Add the trial count to the report so the deflation is auditable.
9. **Treat market text as untrusted input and provenance as the control.** The retrieval layer mints provenance ids; the LLM may only cite ids it was given, and any citation outside that set fails the record [12]. Never give the LLM a URL-fetch, file-read or order tool of any kind — "avoid open-ended extensions" [4]. Render fetched news/filings as text with images and links stripped (EchoLeak's exfil used reference-style Markdown and auto-fetched images [12]).
10. **Make the MCP surface a hardened boundary, not a convenience API.** Hash-pin tool descriptions and diff them on every connect (tool poisoning hides instructions in the description field [55]); run MCP servers with no filesystem or network egress beyond their one purpose; never expose MCP Inspector or an unauthenticated proxy (CVE-2025-49596 is RCE on the developer host via an unauthenticated proxy [56]); follow OWASP's secure-MCP guidance [59]; and map the design to ASI01 Goal Hijack and ASI02 Tool Misuse explicitly in the threat model [6].
11. **Automate the ops surface with boring primitives.** Windows: NSSM service with `AppExit=Restart`, `AppThrottle`, `AppRestartDelay`, stdout/stderr redirection + rotation [42], triggered at boot by Task Scheduler [43]; configure an explicit NTP peer list (≥3) and alarm on offset [44]. Containers: `unless-stopped` restart policy, and do not stack it on a host process manager [45]. Liveness: a `/healthz` that checks *gate + broker connectivity + clock offset + data staleness*, not just process aliveness [46]. Heartbeat: dead-man's switch with an explicit grace window so a brief restart does not page [47]. Logging: OpenTelemetry log records with distinct `Timestamp`/`ObservedTimestamp` so staleness is queryable [40]; alerts follow the four golden signals and the "actionable, novel, requires intelligence" test, reviewed quarterly as incidents per shift [39].

Cadence: one drill per week on rotation; the drill log is a committed artifact; a failed drill blocks live promotion. This is the operational reading of Principles of Chaos (define steady state, hypothesise, inject, try to disprove; automate continuously; minimise blast radius) [48], and of NIST MP-5.1-005's explicit "chaos testing" action [7].

### D. CI rule: CI must never touch a real broker or a real key

The rule, stated as four independently-testable clauses:

1. **No credentials in CI.** Broker and vendor keys live only in the runtime environment of `orderd`; the CI environment has no `APCA_*`/`ALPACA_*` variables set. A test asserts their absence and fails if present [4][31].
2. **Paper-only, opt-in, non-default.** The default base URL in code is paper (`https://paper-api.alpaca.markets` [30]) and reaching live requires an explicit, loudly-named opt-in that CI never sets. Prefer the SDK default and force the override through one function.
3. **Recorded fixtures, replay-only.** All broker and vendor interactions in tests are recorded HTTP sessions replayed offline; the docs' own recommendation is that "calls to Alpaca can be stubbed or mocked" for load testing, with latency sampled from production [31]. This is also what makes golden-file order-lifecycle tests possible.
4. **Network deny + a repo-wide grep gate.** CI runs with outbound access denied to the broker hosts, and a grep gate fails the build if a live URL, an API key pattern, or a bare `alpaca.markets` live host appears in test code. This mirrors the "no test may reach a real system" discipline of §F and the standing obligation to keep adversarial testing *in* CI while keeping live endpoints *out* [7][18].

Corollary: the drills in §C that *do* need a broker run against paper, are executed by a human-invoked runbook (not CI), and are logged as drill artifacts. This keeps the CI/no-broker rule absolute while still exercising the live-shaped paths.
